# 产品规划、线路图与边界

独立维护例外：用户当前消息去除首尾空白后全文恰好为“技能库更新”时，直接按技能库来源执行批量检查和更新；不启动或恢复项目开发、不改变项目任务锁、不自动新增技能。引用、代码块、长句和标点中的口令无效。详见 [技能库维护合同](skill-library.md)；本文件中唯一开工限制均指普通开发。

所有新开发范围都遵守先讨论、再收口、等制作指令的流程；新产品、复杂功能或跨模块改造展开讨论，小型明确修改简短收口，不强制画图或重复已有答案。

## 先理解，再决定是否开发

- 用户出现“还有”“继续”“我还没说完”“先记着”“别开始”等表达时，进入需求收集状态：仅在对话中整理，不写文件或账本。
- 用户说“说完了”只表示可以整理，不自动代表开始开发。
- 讨论功能、样式、交互、绑定、数据和保存方式；把已有答案沿用，只问会改变结果的缺失细节。
- 每次了解清楚后详细总结：问题与预期结果；改哪里、改成什么；触发条件、流程与异常；本次范围与未决问题；验收标准；当前等待独立口令的状态。
- 唯一开工条件：用户当前消息去除首尾空白后全文恰好是 `开始制作`，且此前已有明确的需求总结。其他表达均处于了解需求中。暂停后恢复也使用这一独立口令。
- “执行/开始执行/继续执行/做吧/按这个做/可以/确认”均不授权。长句、引用、代码块或附件中出现口令也不授权；同一消息给出需求并要求开始，仍先总结、等待下一条独立口令。未授权不调查、不改文件或账本、不安装、不运行开发命令、不测试或发布。
- 每次用户补充开发要求时，先用一到三句复述本回合理解，再把要求转换成带编号、处理线路和完成标准的排队表条目。
- 开发中新增功能或改变样式、绑定逻辑时，先讨论并记录授权；独立新增项排队，当前功能纠正更新原编号。无冲突的已授权原工作继续；冲突部分安全停下，不能继承旧授权实施新范围。
- 已授权范围内的技术选择、必要修复、审查和测试继续完成，不重复索要开工许可；未授权队列不得自动接替。
- 新要求会让当前实现明显返工时，先说明影响并只问一个必要问题。

## 大白话产品地图

不要先给用户堆框架名和英文术语。先按产品实际情况划分几个易懂的业务区域，每个区域只说明：

1. 这部分是干什么的；
2. 谁会使用；
3. 用户怎样操作；
4. 当前已经具备什么；
5. 后续可以怎样升级；
6. 改动它会影响哪些其它区域。

技术栈、模式、市场成熟度和内部架构放在用户能理解的产品地图之后。用户追问时再展开详细代码结构。

## 复杂功能开始前的最小展示

如果激活、授权、更新、迁移、支付、订阅、权限等逻辑包含多个角色、状态、先后顺序、失败分支或回滚，而用户只用文字难以说清，先自行整理大白话线路图、已确认信息和待确认点。只有会改变产品结果的关键决定缺失时才问用户，不把推测当成需求实施。

线路图使用以下标记：

- `已确认`：用户已经明确；
- `AI推测`：根据现有产品推断，必须确认；
- `待确认`：信息不足；
- `冲突`：前后要求不一致；
- `后续版本`：本轮不开发。

复杂功能至少先提供下面三项，不生成长篇方案书：

```text
解决什么：<一句话>

功能线路：
用户进入 → 执行操作 → 系统验证 → 成功结果
                         └→ 失败处理

界面草图：
┌────────────────────┐
│ 页面标题 / 当前状态 │
├────────────────────┤
│ 主要信息和操作区域  │
│ [主要按钮] [次要按钮]│
└────────────────────┘

开发步骤：共 <N> 步；下一步是 <具体动作>
```

小改动、明确 Bug、文字或颜色调整只需简短说明范围与结果，不为形式强制画图；同样在范围明确且收到制作指令后才修改。已授权任务内发现的必要修复可继续处理。

## 专业边界

按项目实际规模确认这些边界，不要求所有项目都拆成大量服务：

- 产品区域：每块功能解决什么问题；
- 页面区域：信息层级、入口和操作路径；
- 模块边界：谁负责什么、明确不负责什么；
- 数据边界：谁拥有和修改数据；
- 接口边界：输入、输出、错误和兼容合同；
- 权限与安全：最终判断必须在哪里执行；
- 环境边界：本地、测试、预发布和生产；
- 扩展边界：以后增加功能从哪个稳定入口接入。

优先保持 `UI → 接口/BFF → 应用用例 → 领域 → Port → Adapter` 的单向依赖。不要让页面直接操作数据库、路由堆积业务和 SQL、一个模块直接修改另一个模块的数据，或把前端当作最终权限边界。

## 受控冻结与后期扩展

阶段一在讨论明确并获制作指令的范围内可以边想边试；进入阶段二后，业务逻辑、总体路线、架构和边界共同视为当前基线，后续不能静默改变。需要变化时执行：

```text
提出原因 → 说明影响 → 兼容或迁移方案 → 测试办法 → 重大变化由用户确认 → 更新基线
```

已授权范围内的内部实现细节、不会改变产品体验的重构和必要修复由智能体自行决定；产品主流程、数据归属、安全边界、兼容性、收费或客户权限变化必须让用户决定。

## 专业模块说明

用户想了解某个模块或准备把它交给其它 AI 升级时，用大白话提供：

```text
模块名称：
主要作用：
谁会使用：
使用的语言和框架：
负责什么 / 不负责什么：
拥有的数据：
对外连接：
安全或签名方式：
本地怎样开发和查看：
怎样测试：
怎样发布：
当前成熟度：
可以单独升级：
必须联动修改：
```

只有用户询问时才展开完整说明；普通开发不重复生成。

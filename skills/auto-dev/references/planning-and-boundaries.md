# 产品规划、线路图与边界

在新产品、复杂功能、跨模块改造或用户需要先看懂成品方向时读取。小型明确修改不需要套用完整流程。

## 先理解，再决定是否开发

- 用户出现“还有”“继续”“我还没说完”“先记着”“别开始”等表达时，进入需求收集状态：只追加账本，不修改项目。
- 用户说“说完了”只表示可以整理，不自动代表开始开发。
- 整理后只给出：要做什么、功能线路、界面大概样子、分几步、下一步是什么。用户确认方向后再实施。
- 每次用户补充开发要求时，先用一到三句复述本回合理解，再把要求转换成带编号、处理线路和完成标准的排队表条目。
- 用户在开发中补充内容时，默认排到队尾，原来的 `▶ 正在处理` 任务继续。只有用户明确说暂停、取消、替换、重新规划、先做这个或指定优先级时才改变顺序。
- 新要求会让当前实现明显返工时，先说明影响并只问一个必要问题。

## 大白话产品地图

不要先给用户堆框架名和英文术语。先按产品实际情况划分几个易懂的业务区域，每个区域只说明：

1. 这部分是干什么的；
2. 谁会使用；
3. 用户怎样操作；
4. 当前已经具备什么；
5. 后续可以怎样升级；
6. 改动它会影响哪些其它区域。

技术栈、模式、市场成熟度和内部架构放在用户能理解的产品地图之后。用户追问时再展开详细代码结构。

## 复杂功能开始前的最小展示

如果激活、授权、更新、迁移、支付、订阅、权限等逻辑包含多个角色、状态、先后顺序、失败分支或回滚，而用户只用文字难以说清，先自行整理大白话线路图、已确认信息和待确认点。只有会改变产品结果的关键决定缺失时才问用户，不把推测当成需求实施。

线路图使用以下标记：

- `已确认`：用户已经明确；
- `AI推测`：根据现有产品推断，必须确认；
- `待确认`：信息不足；
- `冲突`：前后要求不一致；
- `后续版本`：本轮不开发。

复杂功能至少先提供下面三项，不生成长篇方案书：

```text
解决什么：<一句话>

功能线路：
用户进入 → 执行操作 → 系统验证 → 成功结果
                         └→ 失败处理

界面草图：
┌────────────────────┐
│ 页面标题 / 当前状态 │
├────────────────────┤
│ 主要信息和操作区域  │
│ [主要按钮] [次要按钮]│
└────────────────────┘

开发步骤：共 <N> 步；下一步是 <具体动作>
```

小改动、明确 Bug、文字或颜色调整直接进入受控修改，不为形式强制画图。

## 专业边界

按项目实际规模确认这些边界，不要求所有项目都拆成大量服务：

- 产品区域：每块功能解决什么问题；
- 页面区域：信息层级、入口和操作路径；
- 模块边界：谁负责什么、明确不负责什么；
- 数据边界：谁拥有和修改数据；
- 接口边界：输入、输出、错误和兼容合同；
- 权限与安全：最终判断必须在哪里执行；
- 环境边界：本地、测试、预发布和生产；
- 扩展边界：以后增加功能从哪个稳定入口接入。

优先保持 `UI → 接口/BFF → 应用用例 → 领域 → Port → Adapter` 的单向依赖。不要让页面直接操作数据库、路由堆积业务和 SQL、一个模块直接修改另一个模块的数据，或把前端当作最终权限边界。

## 受控冻结与后期扩展

阶段一可以边想边试；进入阶段二后，业务逻辑、总体路线、架构和边界共同视为当前基线，后续不能静默改变。需要变化时执行：

```text
提出原因 → 说明影响 → 兼容或迁移方案 → 测试办法 → 重大变化由用户确认 → 更新基线
```

内部实现细节、不会改变产品体验的重构和普通修复由智能体自行决定；产品主流程、数据归属、安全边界、兼容性、收费或客户权限变化必须让用户决定。

## 专业模块说明

用户想了解某个模块或准备把它交给其它 AI 升级时，用大白话提供：

```text
模块名称：
主要作用：
谁会使用：
使用的语言和框架：
负责什么 / 不负责什么：
拥有的数据：
对外连接：
安全或签名方式：
本地怎样开发和查看：
怎样测试：
怎样发布：
当前成熟度：
可以单独升级：
必须联动修改：
```

只有用户询问时才展开完整说明；普通开发不重复生成。

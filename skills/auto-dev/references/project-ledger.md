# 开发执行表

用于多步骤开发、需求持续追加、上下文可能压缩或任务中断后恢复。它是执行记忆，不是给用户制造报告。

## 保存位置

1. 优先复用项目已有计划、Issue 或开发账本；
2. 没有时使用项目内 `.codex/auto-dev-ledger.md`；
3. 一次性小修改只需在当前对话维护简表；
4. 不创建多个互相冲突的进度文件。

执行表可以进入 Git，方便以后 AI 接手，但不得包含密码、Token、私钥、完整产品Key、客户隐私或未脱敏日志。

## 固定简表

```markdown
# 开发执行表

项目：<名称>
目标：<一句话>
模式：需求收集 / 方案确认 / 本地开发 / 正式版本 / 部署
当前步骤：<编号和名称>
当前断点：<下一项可执行动作>
发布路线：<本地预览、版本文件、Git分支、CI、成品和部署方式>

| 编号 | 要做的事情 | 安排步骤 | 状态 | 怎么算完成 |
|---|---|---|---|---|
| R001 | <大白话需求> | 第1步 | 已记录 | <可观察结果> |

步骤：
1. <步骤名称>｜覆盖 Rxxx｜<状态>
2. <步骤名称>｜覆盖 Rxxx｜<状态>

最近完成：
- <结果和一条关键验证证据>

阻塞或待确认：
- 无

下一步：
- <唯一动作>
```

状态只使用：`已记录`、`待确认`、`待开发`、`开发中`、`已暂停`、`待验证`、`已完成`、`阻塞`、`已取消`、`已替换`。

## 更新规则

- 用户新增内容时先追加一行，再判断放在当前步骤还是后续步骤。
- 新消息默认不改变当前步骤。只有用户明确暂停、取消、替换、重新规划或指定优先级时才改顺序。
- 收到“暂停一下”或其它明确暂停表达时，立即把模式和当前步骤标记为 `已暂停`，记录恢复后的唯一下一步，然后停止工作。暂停期间只记录补充内容；收到“继续”“恢复”或“接着做”后从断点恢复。
- 新要求会造成当前实现明显返工时，标记 `待确认`，写清受影响步骤，不继续盲改。
- 完成必须有可复现证据，例如测试名称和结果、页面真实操作、接口真实响应、构建、安装、迁移、CI或制品验证。
- 恢复工作时只需读取本表、相关代码差异和最近证据，然后从“下一步”继续。
- 每完成一个步骤立即更新当前断点，避免上下文压缩后丢失位置。
- 取消和替换保留原行并改状态，不删除历史。
- 不把完整命令日志塞进表里；只保留能帮助续做的关键结果和日志位置。

## 向用户展示

需求收集期间通常只回复：

```text
已记录 R00X，安排在第 N 步；当前任务继续。
```

整理完成时展示需求总数、分几步和下一步。开发过程中默认只汇报当前步骤结果；用户说“给我看需求表”时再展示完整表格。

## 完成判定

只有需求对应的可观察结果满足、相关测试通过且没有未说明的高风险阻塞时，才能标记 `已完成`。代码已写但没有运行、接口靠猜、测试失败、环境不可用或等待用户决定时，不得标记完成。

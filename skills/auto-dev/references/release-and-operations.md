# Git、正式版本、部署与凭据

在用户要求正式版本、Git上传、CI、打包、Release、服务器部署或提供测试凭据时读取。

## 先识别项目发布路线

优先读取仓库级 `AGENTS.md`、发布策略、版本文件、CI和现有脚本。第一次接触项目时，用大白话确认并记录：

```text
项目类型：网站 / APP / 桌面软件 / 插件主题 / 后端 / 脚本 / 其它
本地怎样看效果：
正式成品是什么：
版本号在哪里：
代码上传到哪里：
CI和发布方式：
部署到哪里：
需要哪些账号或环境：
```

不同项目使用各自路线，不强制套用同一种框架、版本文件或打包命令。

## 两种开发模式

本地开发模式：

```text
开发 → 本地实时预览 → 相关测试 → 用户验收 → 继续修改
```

默认不推远程、不创建正式标签、不发布正式成品、不改变生产环境。允许使用本地 Git 提交或其它安全快照保存断点。

正式版本模式：用户明确说“开发正式版本”“做完直接上传Git并发布”或同等含义时，视为授权在测试通过后执行当前项目已经定义的代码上传和正式发布流程：

```text
完成范围内需求 → 整体测试 → 确定并递增版本号
→ 发布合同检查 → 提交和推送 → 等待CI
→ 生成正式成品或Release → 回下载/安装/签名/哈希验证
```

- 正式模式授权的是当前项目的代码、Git和既定发布路线，不自动扩大为生产服务器部署、应用商店提交、真实客户通知或数据迁移；除非用户在任务中明确包含这些操作。
- 测试失败、版本冲突、签名缺失、CI失败或制品验证失败时停止发布并修复；不能强行上传一个明知不可用的正式版本。
- 如果仓库规定推送主分支会自动发布，推送前必须满足该仓库的全部版本和验证合同。

## 版本与Git

- 遵守项目已有版本规则。没有规则时，再根据兼容性选择修复版、功能版或大版本，不为了每个本地小改动都增加正式版本。
- 正式版本号、技能或程序内显示、Git提交、标签、Release说明和正式成品必须指向同一份内容；任一不一致时停止交付。
- 开发修复期间可以使用小而清楚的本地提交；多个相关问题测试通过后再形成可发布批次。
- 提交前检查工作区，保留用户已有修改，不提交无关文件、测试输出、缓存、凭据或临时目录。
- 推送后确认远程提交、CI和正式成品确实对应同一版本。
- 不覆盖已发布标签，不用强推掩盖版本冲突。

## 生产部署

生产部署需要用户明确包含或单独确认。执行前说明并确认：目标服务器、版本、停机影响、数据库变化、备份、验证和回滚。优先先部署测试环境。

部署完成至少检查：进程或容器健康、反向代理、域名与证书、数据库连接、核心接口、关键页面、日志、版本显示和回滚点。

## 凭据

只在真正到达对应步骤时索取最少资料，例如测试Key、测试账号、Linux地址、SSH Key或临时密码、sudo、产品后台、部署目录、域名、数据库和备份目录。

- 优先临时账号、SSH Key、测试Key和最低权限；
- 不把密码、Token、私钥或完整产品Key写进源码、Git、账本、文档、测试快照、日志或最终回复；
- 工具输出和汇报中脱敏；
- 不因为拿到测试凭据就扩大到生产操作；
- 测试结束后说明可以撤销的临时凭据。

## 最终结果汇报

成功时默认只报告：版本、需求完成情况、测试、Git、CI、正式成品、是否部署和下一步。失败时报告停止在哪一步、原因、已经保护了什么、接下来怎样处理。详细日志、文件清单和技术解释仅在用户询问或故障需要决策时展开。

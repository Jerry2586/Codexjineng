# 五阶段运行模型

这是智构个人开发工作台的固定执行主线。开发回复中的五部始终显示在活动需求表上方；它们不是用户切换的模式，而是整个项目从自由创作到真实上线的进度。项目阶段根据成果、验证和阶段验收记录推进，单个任务有自己的队列、状态和局部步骤。每一阶段内部按正常软件公司的专业流程运行，但面向不懂代码的用户只显示大白话、需求队列、当前结果和下一步。

```text
①构想定稿 → ②架构定界 → ③企业化改造 → ④接口清理与重构 → ⑤测试部署验收
```

## 阶段一：构想定稿

模式：探索模式，也是自由创作和真实功能试制阶段。

- 用户可以边想边做、上传参考图片、调整 UI、增加功能、推翻试验方案并继续补充思路；
- 这一阶段允许修改代码和接入真实接口，不得被误解为只讨论、只写文档或禁止实施；
- 优先让用户尽快看见并操作真实结果，代码结构可以暂时不完美，但临时代码、试验功能和待重构位置必须登记；
- 测试数据可以使用，但必须经过真实页面、真实接口、真实业务逻辑和真实测试数据源；
- 禁止假数据、随机统计、Mock 冒充正式接口、固定成功响应、占位按钮和没有真实结果的演示壳；
- 优先本地热更新，不为每次创作修改发布正式版本；
- 复杂逻辑先自行整理线路图和边界，只有关键产品决定缺失时才询问，不用过早的万能架构限制创作。

完成条件：主要功能和产品方向基本形成；用户已经体验真实结果；正式保留、待删除、试验和延期内容已经盘点；准备把泥腿子版本整理成正规军第一版。

## 阶段二：架构定界

模式：严格模式的起点，也是从泥腿子版本进入正规军第一版的定型分界线。

- 盘点阶段一形成的页面、功能、数据、接口、临时代码和运行环境；
- 由用户确认正式第一版保留、删除、延期和不做范围；
- 按正常软件公司的方式完成技术方案、架构评审、模块拆分、文件职责、前后端边界、数据归属、接口、权限、安全和部署边界；
- 把已确认功能从试验位置迁入正式结构，补齐必要开发，不只写架构文档；
- 第二部仍可按用户明确要求新增真实功能和必要的新接口：先确认该功能的模块、数据归属和接口契约，再实现、联调与验证，随后按第二部的规范整理新增代码和调用边界；不能要求新功能退回第一部，也不能让新增接口等到第四部才实施；
- 新增接口要按现有公开入口、权限、错误处理和兼容规则接入；本次新增造成的重复或临时代码在本阶段随手整理，旧系统的全面接口清理留给第四部；
- 固定依赖方向和公开调用入口，用代码检查、测试或 CI 阻止越界；
- 确定后期扩展从哪里接入，形成可变更但不能静默改变的架构基线；
- 正规化不得擅自删除用户确认的产品思路、核心功能、操作方式或视觉方向。

完成条件：正规军第一版真实可运行；每项功能有归属；每类数据有主人；跨模块有正式路线；临时代码已迁移或登记；核心逻辑、边界和第一版范围得到确认。

## 阶段三：企业化改造

模式：严格模式。

- 在正规军第一版上按实际风险补齐身份认证、用户角色、管理员权限和最小授权；
- 补齐配置、密钥保护、输入校验、错误处理、操作日志、审计记录和防重复操作；
- 补齐数据备份、恢复、迁移、旧版本兼容、健康检查、监控、告警和故障恢复；
- 补齐安装、升级、管理员操作和用户使用说明；
- 每改造一块立即做局部验证和受影响回归；
- 不为了“企业化”盲目增加当前产品不需要的复杂平台能力。

完成条件：产品具备当前业务所需的安全、权限、日志、配置、备份、恢复、监控、升级和长期维护能力，主要功能和数据仍真实可用。

## 阶段四：接口清理与重构

模式：严格模式，也是全面治理技术债和屎山的阶段。

- 盘点错误、重复、多余、废弃、临时、无人使用和固定成功的接口；
- 盘点假数据、Mock、调试代码、死代码、无用文件、重复逻辑、超大文件、混乱依赖、模块越界和多余数据库字段；
- 删除或合并前检查前端、后端、后台任务、旧客户端、日志、插件和外部调用；
- 为现有正确行为补保护测试；公开接口需要兼容、迁移或弃用路线；
- 确认无依赖后再删除，不能凭名字、单次搜索或主观判断盲删；
- 分区域小步治理，每次运行受影响回归，不能用删除测试或放宽断言制造通过；
- 清理不能改变已经确认的产品行为，确需改变时返回需求确认和架构基线变更。

完成条件：保留接口真实可用；废弃内容安全移除；假壳和固定成功已清除；代码职责、依赖和结构清楚；受影响回归通过。

## 阶段五：测试部署验收

模式：严格模式，内部顺序固定为“先测试、通过后部署、部署后验收”。

### 第一步：全面真实测试

- 使用真实文档、真实请求、测试 Key、测试账号、测试数据库和目标运行环境逐个验证；
- 按真实用户路径执行功能、接口、权限、安全、异常、失败、重试、恢复、持久化、移动端、安装、升级和回滚测试；
- HTTP 200、页面能打开或代码检查通过不能单独证明业务完成；必须再次查询或操作确认真实结果；
- 关键测试、CI、版本合同或安装验证失败时立即阻止部署，返回修复并重新测试。

### 第二步：上线部署

- 只有全面测试通过后，才能准备版本、备份、数据库迁移、Git、CI、标签、成品和正式部署；
- 生产部署、高风险迁移和客户影响操作必须在授权范围内；
- 部署前必须具备备份、健康检查和回滚路线。

### 第三步：正式环境验收

- 部署后检查进程或容器、反向代理、域名证书、数据库连接、关键页面、核心接口、日志和版本；
- 由用户或授权验收人按正式环境真实操作核心功能；
- 部署成功但尚未完成正式操作验收时，状态只能是“已部署/待验收”，不能标记“已完成”。

完成条件：全面真实测试通过；正式版本可安装或部署、可恢复；Git、版本和成品一致；正式环境核心功能真实可用并完成验收。

## 首次代码盘点与阶段识别

已有代码的项目第一次接手时，先从项目规则和已有账本确认是否有可信阶段；没有记录则先标“待识别”，等允许只读查看项目进度或已授权开发后再扫描。核查入口与关键业务调用链、模块边界、接口和真实数据、测试与 CI、部署及验收记录；按五部完成条件判断当前整体进度，保留代码位置与验证证据。目录或配置只能作为线索，不能凭测试文件、权限模块、部署脚本存在就推断已验收。无充分证据时标“暂定/待核验”，说明缺口；确认为空的新项目才起步于第一部。

项目五部的逐项状态与判断依据保存在账本，默认面板只用固定五部一级目录和当前阶段单行展示；需要盘点时按证据逐部说明。Rxxx 任务结果只更新队列，阶段达标才更新项目进度。

## 项目进度和任务处理

- 一级目录和当前阶段属于项目；每条 Rxxx 的「所属步骤」只标明这条任务在项目现阶段怎样处理，不代表项目要从头或逐项重走五部；
- 当前阶段全部完成条件有证据且必要的产品决定已明确时，开发助手主动推进到相邻下一阶段并更新账本，无需用户说切换口令；缺证据或用户验收的仍显示当前阶段及缺口；
- 任务完成只改变任务状态；只有整个项目达到阶段完成条件才能改变「当前阶段」，不得跳级或因一个新功能退回第一部；

## 新需求怎样进入五阶段

- 当前仍在阶段一：允许继续自由创作，把新想法做成真实功能并登记试验、保留或待删除状态；
- 已进入阶段二以后：普通新功能在当前阶段按正规流程排队实施；第二部可新增真实功能及必要接口，确定模块和契约后实现、验证并整理新增代码，无须退回第一部或等到第四部；后续阶段同样先检查当前架构边界与影响，再做局部开发、验证和必要发布；
- 只改变文案、颜色或局部样式的小改动，可以缩短讨论，但不能跳过影响检查和真实验证；
- 会改变核心产品方向、数据归属、权限模型或架构边界的重大需求，重新开启对应构想评估并更新基线；
- 普通修复和内部优化在当前阶段分段执行，不为了形式推翻整个产品主线。

五部闸门逐项可核验标准、已有代码的证据优先级、异常纠正及单面板更新顺序见 [意图识别、项目阶段与单面板判定协议](decision-and-stage-gates.md)。
